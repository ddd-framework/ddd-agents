## 1. One runtime, no task mode

There is no "long-running conversation" type. A normal turn becomes a long task the moment the model writes a task
plan (the adoption trigger is in the base prompt: more than one thing → the plan first), or a purpose seeds one. The
behaviour follows from data on the conversation: the plan, the run settings and the initiator type. Purposes and the
plans they seed: `ddd-module-agents-skills-and-purposes-specialist`.

## 2. The plan and where it lives

`TaskPlan` → `TaskPlanItems` → `TaskPlanItem` (with `subtasks` of the same set type, any depth, no item limit). The
active plan is `AgentWorkingState::$taskPlan`; finished plans are `AgentWorkingState::$completedTaskPlans`. Both live in
the conversation's `agentWorkingState` JSON column, which merges slices (RFC 7396): `TaskPlan::mapToRepository()` emits
every key and the item tree as plain arrays, so a slice replaces the plan whole; a clear needs an explicit null.

The plan is written at loop level by `AIConversationsService::persistTaskPlanSlice($conversation, $taskPlan, $runToken)`
(token-fenced; the `taskPlanOpenAt` / `taskPlanRetryableAt` markers ride the same statement), column first, then the
tool-call row — a missing call row is regenerated by a re-driven turn, the reverse would claim an update that never
landed. The two plan tools are `TaskPlan::PLAN_TOOL_NAMES`; every exemption (repeat guard, read dedup, work-tool folds,
the forced step) consults that list, never a single tool name. The record service that applies their calls,
`AIConversationTaskPlanRecordService`, belongs to `ddd-module-agents-skills-and-purposes-specialist`.

Two stamps drive everything turn-related: `updatedAtTurnInitiatorMessageIndex` (any write in a turn) and
`resolvedAtTurnInitiatorMessageIndex` (an item moved to a terminal status). Both hold the persisted index of the turn's
initiator message, never a derived turn count (a compaction between chunks would shift a count).
`wasUpdatedInTurn()` / `wasResolvedInTurn()` compare them with `AIConversationMessages::getNewestInitiatorMessageIndex()`.

## 3. Keys

Every item carries a key the server mints and keeps (`7.2.11`): one segment per level, 1–999, no leading zero
(`TaskPlanItem::KEY_PATTERN`, `KEY_SEGMENT_MAX`).

- A key is minted once from its parent's counter (`TaskPlanItem::$highestSubtaskKeyNumber`, the plan's
  `$highestItemKeyNumber`; `mintTopLevelKey()`, `mintSubtaskKey()`), never renumbered, never reused within the plan.
- A level that used all 999 numbers takes no new item; `allocateKeySegmentAfter()` answers null.
- Order and the `← next` marker follow the stored order, never the key. A plan never restructured has key = number
  path, so its render does not change.
- A stored tree whose keys are irregular gets `TaskPlan::$keyIntegrityViolations` on read (transient, never persisted).

## 4. `update_task_plan`

Structure only, keyed (`UpdateTaskPlanTool`, arguments `UpdateTaskPlanArguments`):

- an existing item: `{"key": "2.1"}` — its text is fixed; a different text rejects;
- a new item: `{"text": "…"}` without a key — the server mints the key;
- a drop: `{"key": "…", "remove": true}`; an existing item sent without `subtasks` keeps its subtree.

`TaskPlan::checkUpdate()` collects every violation in one pass (`TaskPlanUpdateRejections`): unknown or malformed key,
a key sent as a number or another JSON type, an item of a listed level left out, a move, a changed text, the last item
or the last child dropped. One violation rejects the WHOLE call — nothing changes, no counter, no stamp — and the result
names every line, the plan's keys and the valid shapes. `applyUpdate()` applies an accepted call to a deep copy that
keeps every stored item with its declarations, records and status (`TaskPlanUpdateApplication`); a call that changes
nothing is `unchanged`. Without items the call is a creation (`createFromUpdate()`, keys minted in pre-order).

A status sent on an item passes the same tick application as `set_task_status`
(`applyStatusUpdatesWithoutTheTurnStamps()`); the stored status again is no transition, and a status never rejects
the call. A conversation whose purpose seeded its plan is not offered `update_task_plan` at all.

Every plan-tool call records `ToolCall::$taskPlanCallOutcome` (`ToolCall::TASK_PLAN_CALL_OUTCOME_*` (applied keyed,
unchanged, refused)).

## 5. `set_task_status`

Progress ticks addressed by key, strictly (`SetTaskStatusTool`, `SetTaskStatusArguments`): only a conforming key that
names exactly one item addresses it; anything else rejects the whole call with the open keys listed
(`SetTaskStatusAddressCheck`). Per update, in the order sent, `TaskPlan::applyStatusUpdates()` runs the echo check of
this turn's platform closing, the cascade cap, then the item's gates and transition (`TaskPlanItemTickGate`).

- **The cascade cap:** more than `TaskPlan::MAX_BLOCKED_UPDATES_PER_CALL` items moved to `blocked` (or to
  `not_applicable`) in one call is a give-up sweep: every such update is noted, not applied.
- **Record-gated items** (`TaskPlanItem::isClosedByThePlatformFromTheRecord()`: a named tool call, a widget, a connected
  channel or a criterion): a model tick applies only when the record confirms it — a tool-call or widget gate admits a
  `done` tick when its evidence is on the record. On a criterion leaf a still-open verdict refuses the tick and a
  resolved verdict replaces it; an undecided criterion refuses a `done` tick only under a purpose whose
  `AIConversationPurpose::enforcesDoneCriterionOnTicks()` holds. A tick the record cannot confirm is not applied; the
  item stays open and closes itself from the record. Which verdicts exist: `ddd-module-agents-skills-and-purposes-specialist`.
- **A call the model could not know was redundant:** when every update of a call named an item the platform resolved
  after the model wrote the call, the result starts with `SetTaskStatusTool::RESULT_PREFIX_NO_CHANGE_NEEDED` and the
  call counts as completed.
- **The echo of a platform closing:** the first tick in a turn of an item the platform closed in this turn is answered
  "nothing to do" (`TaskPlanItemTickGate::checkEchoOfThisTurnsPlatformClosing()`); a second tick of the same item takes
  the same-status path below.
- **A tick that repeats the item's stored status** changes nothing and has three answers
  (`TaskPlanItemTickGate::answerSameStatusReTick()`): an item whose stored status is terminal while its subtasks are
  still open gets a line that names the open subtasks by key and is not counted as a no-op; the first true no-op of a
  call carries the long instruction, once per call; every further one in the same call is one short line. None of
  them counts as applied, so a call in which nothing was applied or noted is marked FAILED
  (`AgentTaskPlanTickOutcome::failsTheCall()`), and that failed tick counts toward the brakes of section 9.
- **A later tick replaces a run-time status note:** a same-status tick with a non-empty `statusNote` overwrites the
  item's note (`TaskPlanItem::refreshStatusNoteUnlessPreResolvedAtSeed()`, called from
  `TaskPlanItemTickGate::applyTick()`). Only an item the platform resolved when the plan was seeded keeps its note,
  which states what the record shows.
- **The all-no-op breaker:** a call that applied no update and carried at least one true no-op (the one with the long
  instruction; a re-tick of an item with open subtasks does not count, `AgentTaskPlanTickOutcome::isAllAlreadyInStatus()`)
  forces the tool-less answer step only when no open item remains, when an earlier tick of the turn failed while no
  item carries `← next`, or after `AgentTaskPlanTickOutcome::LOOPING_FAILED_TICKS_IN_A_TURN` failed ticks
  (`AgentTaskPlanTickOutcome::requiresToolLessAnswerStep()`). Forcing on the first redundant tick while workable items
  remain made the model announce the next item instead of doing it.
- **The judgement is read lazily:** for the statuses an `update_task_plan` call sends, the evidence and the criteria a
  tick is judged by are read only when a status transition reaches the gates
  (`TaskPlanUpdateContext::forStatusTickOfConversation()`); a call whose statuses change nothing reads none of it.
- The tick feedback lines are returned verbatim in the call's result; nothing is silent.

**The plan note after a work tool.** When a work tool completes, the platform re-sweeps the plan first and then appends
one note to the call's result (`ToolCall::$resultAppendix`, written by
`AIConversationTaskPlanRecordService::closeLeavesProvenByCompletedToolCallAndAppendPlanNote()`): the items it closed
from the record, named with their verdict and "do not tick", and the items whose tick the model owes and will be
accepted (`TaskPlanItems::getItemNumberPathsTickableAfterToolCall()`). The note is built from the plan as it stands after
the re-sweep — a note written before it asked for ticks of items the platform closed a moment later. A call the loop
answered without running it (a refused repeat, a read answered from an earlier result) carries no note.

## 6. Openness and the item states

`TaskPlanItem::STATUS_OPEN`, `STATUS_DONE`, `STATUS_BLOCKED`, `STATUS_NOT_APPLICABLE`; a `statusNote` says what was
produced, the obstacle or the reason (capped at `STATUS_NOTE_MAX_LENGTH`). A blocked item carries
`requiresUserAction` (only the owner can lift it) and `retryable` (a transient external failure).

`TaskPlanItem::isOpen()` is tree-aware and the ONE predicate every reader uses: blocked and not_applicable prune their
subtree; a done item with open subtasks stays open; an open container whose subtasks are all terminal is closed (the
model ticks leaves, never containers).

## 7. What the model reads

Each call carries the plan as a tail entry (`TaskPlan::toTailHintText()`): a header with the one tick rule set
(`TaskPlan::buildTickRules()` — also the tool description and the maintenance rules), then one compact line per item
(key, status, title; the full text only for the `← next` item; finished subtrees collapsed). Because it is re-derived
from the column, it survives tool-result clearing, compaction and a worker hand-over. Placement in the model input:
`ddd-module-agents-context-specialist`.

Two wire rules keep the plan calls cheap and their lessons in context. Every `update_task_plan` call below the newest
one sends its arguments stubbed as `{"superseded":true}` (`AIConversationMessage::toOpenAiToolCallEntryArray()`; call id
and name stay, so call and result still pair) — the current plan is in the tail entry, and forensics read the persisted
rows. The results of the plan tools are exempt from tool-result clearing: the creation result carries the maintenance
rules once per run, every tick result is a one-line count, and the clearing stub's "call again" would invite exactly the
full-plan resend the rules forbid. `ToolCall::readTaskPlanCallOutcome()` gives the outcome of a row stored before
`$taskPlanCallOutcome` existed (failed → refused, a no-op resend → unchanged, otherwise a full replace).

## 8. Budgets and chunks

A plan raises the turn's budget (`AIConversationTurnBudget`, see [architecture-of-a-turn](architecture-of-a-turn.md) §7): a turn whose plan was
touched in this turn gets base steps plus steps per leaf, clamped, and the default cost cap as a second brake; explicit
`RunSettings::$maxStepsPerTurn` and `$maxTurnCostUsd` always win. The budget is re-derived at every step, so a plan
created at step 1 raises its own turn and a shrinking plan lowers it. Steps consumed are counted from the persisted
usage-stamped rows.

A worker invocation runs at most `AIConversationTurnBudget::MAX_STEPS` steps, then yields: a `TURN_CONTINUATION`
signal, the handover marker, a re-fire. The next invocation re-claims, reloads the cover and the tail and continues
the same turn. Sync paths run the remainder inline. One step before the budget, the last call runs without tools (the
budget closing step); its text becomes the owner's message with a pause footer when work remains.

## 9. The checked stop and the brakes

The loop asks `AgentCheckedStopPolicy::shouldBounceCheckedStop()` before it accepts a final text: a plan touched in this
turn (or a turn a work signal started), items still owed once the candidate text's own evidence is counted
(`TaskPlanItems::hasOwedOpenItemsAfterCandidateTextEvidence()`), and a text that hands nothing to the owner → the text is
discarded and bounced with `SIGNAL_SOURCE_TASK_PLAN_OPEN_BOUNCE`, at most `MAX_BOUNCES_PER_CHUNK` per chunk. The bounce
is ONE text (`AgentCheckedStopPolicy::buildCheckedStopBounceText()`): the owed items by key, split into the ones the
model ticks and the ones the record closes. A plan-less turn is never bounced, nor is the opener of a kickoff the owner
has not answered yet (`AIConversationMessages::isKickoffBeforeTheOwnerSpoke()`). The site and its other bounces: [stall-and-final-text](stall-and-final-text.md).

Plan tools are exempt from the repeat guard, so two brakes keep a re-tick loop finite:
`AIConversationAgentService::MAX_CONSECUTIVE_REJECTED_PLAN_TICKS` and `MAX_REJECTED_PLAN_TICKS_PER_TURN` hold the plan
tools back for the step, and `AgentTaskPlanTickOutcome::LOOPING_FAILED_TICKS_IN_A_TURN` forces the tool-less answer
step. Under append-only loading the tools stay on the wire and the dispatch refuses them
(`AgentStepToolRestriction::markPlanToolsHeldBackAfterRejectedTicks()`): one such refused call (marked
`ToolCall::$wasWithheldOnStep`) forces the tool-less answer step, and a withheld refusal never counts as a rejected tick,
so it never re-arms the brake.

## 10. Finished plans

An accepted final answer on a finished plan (`TaskPlan::isFinished()`) retires it into the finished set
(`AIConversationTaskPlanRecordService::retireFinishedTaskPlanIfDue()` → `AgentWorkingState::retireFinishedTaskPlan()`,
`TaskPlan::retire()` stamps title, time and `outcomeSummary`), and the next owner turn starts plan-less. This happens only
for a model-created plan of a root conversation whose purpose neither works autonomously nor seeds its plan, and only
while the plan-dynamics decision site (`AgentDecisionModelSettings::SITE_PLAN_DYNAMICS`) is on; in shadow mode the
retirement is only recorded (`wouldRetireFinishedPlan`) and the plan stays active. `get_task_plans` (`GetTaskPlansTool`) reads the finished plans. A finished plan reopens for
the owner's very next message when the turn right before wrote and retired it (`TaskPlan::reopensForOwnerTurn()`,
`reopen()`), so an amendment adds items instead of starting over. The reopen
(`AgentPlanDynamicsDecisionsService::reopenFinishedTaskPlanOfThePreviousOwnerTurnIfDue()`) records the platform's
decision (`AgentPlanDynamicsDecision::buildForReopenedPlan()`) instead of asking the plan question, and the model reads
`AgentPlanDynamicsDecision::buildReopenedPlanDirective()`: added parts go in as new items with `update_task_plan` as the
first call, the finished items kept by key; an owner message that adds nothing is just answered and the plan closes
again. The directive stops once a plan update of the turn applied.

## 11. Long unattended runs

A run without the owner (an initiator type in `AIConversation::getOwnerAbsentInitiatorTypes()`) runs the same chain:
chunks, checked stop, the terminal report on a cut turn, and the recovery passes when a hand-over is lost. Schedules,
owner reports and their delivery duty: `ddd-module-agents-autonomy-specialist`.

## 12. Tracing a plan

`AIConversationMessage::$taskPlanSnapshot` holds the plan tree as it stood after the write a message caused — the
column write first, the snapshot on the message's own insert, identical repeats skipped. A truncate is a soft delete,
so snapshots of an abandoned branch survive. A truncation at or below the plan's initiating turn clears the plan and the
handover marker (`driveConversation()` with a truncate index). The generic trace events: `ddd-module-agents-observability-specialist`.
